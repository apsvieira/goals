# Streaming Sync — Design Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Replace the batched operation queue with immediate, self-contained event streaming to eliminate data loss from interrupted syncs. Simplify the dual ID scheme along the way.

**Problem:** The current sync system queues operation *references* in IndexedDB and reconstructs entity state at sync time (every 2 minutes). If the app navigates, crashes, or loses connectivity during that window, queued operations can become irrecoverable because the local state they reference may have changed or been cleared.

**Architecture:** Each user mutation produces a self-contained event (full payload, no entity lookups) written to IndexedDB, then immediately POSTed to a new `POST /api/v1/events` endpoint. Failed sends stay in the event log and are flushed on reconnect. The server processes events through the existing LWW merge logic with an idempotency table to handle duplicates.

**Tech Stack:** Svelte 5, TypeScript, idb, Go, SQLite

## Design Decisions

### ID Scheme

| Entity | Current | New | Generated by |
|---|---|---|---|
| Goals | `local-${Date.now()}-${random}` | `crypto.randomUUID()` | Client |
| Completions | `local-*` (client) / UUID (server) | `{goal_id}:{date}` (deterministic) | Both |
| Events | `local-*` | `crypto.randomUUID()` | Client |

- Goals use standard UUIDs. No more `local-*` prefix.
- Completions have a natural composite key `(goal_id, date)`. Making the ID deterministic from that pair means client and server always agree. The server's `generateCompletionID()` in `merge.go` adopts the same derivation.
- Existing `local-*` IDs in the wild continue to work — the server already accepts any string ID.

### Event Format

The current `QueuedOperation` stores a type and an `entityId` reference. The new `SyncEvent` carries the full payload:

```typescript
interface SyncEvent {
  id: string;                // crypto.randomUUID()
  type: "goal_upsert" | "goal_delete" | "completion_set" | "completion_unset";
  timestamp: string;         // ISO 8601, set at creation
  synced: boolean;           // false on create, true after server ACK
  payload:
    | { id: string; name: string; color: string; position: number;
        target_count?: number; target_period?: "week" | "month" }  // goal_upsert
    | { id: string }                                                // goal_delete
    | { goal_id: string; date: string }                             // completion_set
    | { goal_id: string; date: string };                            // completion_unset
}
```

Operation types collapse from six to four: `create_goal`/`update_goal` → `goal_upsert`, `reorder_goals` → N individual `goal_upsert` events each carrying the new position.

### Client Send Flow

```
User action
  → write SyncEvent to IndexedDB (synced: false)
  → update local state (goals/completions stores, as today)
  → fire sendEvent(event) — non-blocking, no await
```

**`sendEvent(event)`:** POST the single event to `/api/v1/events`. On success, mark `synced: true`. On failure, leave it — flush picks it up later.

**`flushPendingEvents()`:** Read all events where `synced === false` ordered by timestamp. POST them as a batch to `/api/v1/events`. Mark all returned IDs as `synced: true`.

**Flush triggers:**
- App startup (after auth)
- Coming back online (`online` event on `navigator`)
- Every 5 minutes as a safety net (fallback, not primary path)

### Server Endpoint

**`POST /api/v1/events`** accepts `{ "events": [...] }`.

For each event, the handler translates to the existing merge types:

| Event type | Translation |
|---|---|
| `goal_upsert` | `GoalChange` with `Deleted: false` → `MergeGoal` → `UpsertGoal` |
| `goal_delete` | `GoalChange` with `Deleted: true` → `MergeGoal` → `UpsertGoal` |
| `completion_set` | `CompletionChange` with `Completed: true` → `MergeCompletion` → `UpsertCompletion` |
| `completion_unset` | `CompletionChange` with `Completed: false` → `MergeCompletion` → `UpsertCompletion` |

**Idempotency:** A `processed_events` table stores `(event_id TEXT PRIMARY KEY, processed_at TIMESTAMP)`. Duplicate event IDs are skipped. Rows older than 30 days are pruned periodically.

**Response:** `{ "processed": ["event-id-1", "event-id-2", ...] }`. Duplicates are included in `processed` — from the client's perspective, they're done.

**Remote changes from other devices** continue to come through `GET /api/v1/calendar?month=`. The old `last_synced_at` pull mechanism in the sync endpoint is no longer needed.

### Migration (one-time, client-side)

On app startup, before the first flush:

1. Read all entries from the `operations` IndexedDB store (old queue format).
2. For each, build a `SyncEvent` by reading the entity from local state — same reconstruction `sync()` does today, but only this one last time.
3. Write the new events to IndexedDB with `synced: false`.
4. Delete the old `operations` entries.
5. Proceed with normal flush.

If the old queue is empty (typical), this is a no-op. The `operations` store is dropped in a subsequent IndexedDB version bump (v2 → v3) after one release cycle.

## Trade-offs

### Gains

- **Near-zero data loss window.** Events persist to IndexedDB before the send attempt. The 2-minute batch window collapses to single-digit milliseconds.
- **No state reconstruction.** Self-contained events need zero entity lookups at send time. The current `sync()` reads all goals/completions per queued operation.
- **Idempotent retries.** Server-side event ID tracking means duplicate sends are harmless. Today, a crash between server acceptance and queue clearing causes a full re-send.
- **Simpler `getCalendar()`.** The reconciliation hack (api.ts:132-153) that merges pending local ops with server responses goes away — events land on the server within milliseconds.
- **Simpler ID model.** One UUID per goal, deterministic IDs for completions. No client/server mismatch.
- **Audit trail.** Synced events stay in IndexedDB (marked `synced: true`) instead of being deleted. Useful for debugging, prunable periodically.

### Losses

- **More HTTP requests.** One POST per mutation instead of one batch every 2 minutes. Negligible at 5-20 daily mutations.
- **No batched conflict resolution.** Events are resolved independently. In practice this doesn't matter — LWW is already per-entity.
- **Server storage for idempotency.** The `processed_events` table is new state, though small and TTL-prunable.
- **Migration effort.** One-time conversion of old queue entries on app startup.

## Testing Strategy

| Test | Verifies | Type |
|---|---|---|
| Create a goal offline, come back online | Event persists in IndexedDB, flush sends it, server has the goal | E2E |
| Create a goal online | Event sent immediately, `synced` flips to true, `getCalendar` returns it | E2E |
| Kill the app mid-request (abort controller) | Event remains `synced: false`, next flush resends, server deduplicates | Integration |
| Send the same event ID twice | Server returns both in `processed`, no duplicate entity | Backend unit |
| Flush 50 events in a batch | All marked synced, server state correct | Integration |
| Old queue migration | `operations` store populated → converted to `SyncEvent` → old store emptied | Frontend unit |
| Deterministic completion IDs | Client and server derive same ID from `(goal_id, date)` | Unit (both) |
| `goal_upsert` with stale timestamp | LWW rejects — server copy is newer | Backend unit |
| Two devices, conflicting edits | Each sends events, LWW resolves, both see winner on next `getCalendar` | E2E |

## Implementation Order

### Task 1: ID scheme change

**Files:**
- Modify: `frontend/src/lib/api.ts` — replace `generateId()` with `crypto.randomUUID()` for goals/events, `${goalId}:${date}` for completions
- Modify: `backend/internal/sync/merge.go` — change `generateCompletionID()` to return `goalID + ":" + date`

Low risk, standalone change. Existing `local-*` IDs remain compatible.

**Tests:** Unit tests for both ID generation functions. Verify existing goals with `local-*` IDs still sync correctly.

### Task 2: SyncEvent type and IndexedDB storage

**Files:**
- Modify: `frontend/src/lib/storage.ts` — add `events` object store (IndexedDB v3), add `saveSyncEvent()`, `getUnsyncedEvents()`, `markEventsSynced()` functions
- Create: `frontend/src/lib/events.ts` — `SyncEvent` interface definition

Write events alongside old operations (dual-write) so the new store is populated but not yet used for sending.

**Tests:** Unit tests for IndexedDB event CRUD. Verify v2 → v3 upgrade migration.

### Task 3: Server `POST /api/v1/events` endpoint

**Files:**
- Create: `backend/internal/sync/events.go` — event-to-change translation, handler logic
- Modify: `backend/internal/db/queries.go` — add `processed_events` table queries (insert, check, prune)
- Modify: `backend/internal/db/migrations/` — migration for `processed_events` table
- Modify: `backend/cmd/server/main.go` (or router file) — register new route

**Tests:** Backend unit tests for event processing, idempotency (duplicate event ID), and each event type → merge path.

### Task 4: Client sendEvent and flushPendingEvents

**Files:**

**Tests:** Integration tests with mocked fetch: immediate send success, immediate send failure + flush retry, offline queueing.

### Task 5: Remove old sync code

**Files:**

- Modify: `frontend/src/lib/storage.ts` — remove `saveQueuedOperation`, `getQueuedOperations`, `deleteQueuedOperation`, `clearQueuedOperations`

**Tests:** Verify no regressions in E2E calendar flow. Verify old sync endpoint still works (for older clients in the wild during rollout).

**Tests:** Frontend unit test: populate `operations` store with old-format entries, run migration, verify `SyncEvent` entries created and `operations` cleared.

### Task 7: Drop operations store

**Files:**
- Modify: `frontend/src/lib/storage.ts` — bump IndexedDB to v4, remove `operations` store in upgrade handler

Ship this one release cycle after Task 6 to ensure all clients have migrated.
